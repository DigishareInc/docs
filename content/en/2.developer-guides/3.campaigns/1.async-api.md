title: Asynchronous API
description: Queue campaigns through the event gateway and let the platform create them in the background.

The asynchronous API accepts a campaign as an event on `api-app.digishare.ma` and answers as soon as the event is queued. The platform then creates the campaign in the background, with the same rules as the standard Campaigns API. Use it for high-volume or fire-and-forget integrations that do not need the created campaign in the response.

::note
**Prerequisites**:

- A valid **Bearer Token**, the same one you use on `api.digishare.ma` (see [Authentication](/developer-guides/authentication)).
- A campaign payload that works with `POST https://api.digishare.ma/v1/campaigns`.
::

## Standard or Asynchronous

Both endpoints accept the same payload and create the same campaign. They differ in what they return and in how much they accept.

| | Standard API | Asynchronous API |
| :--- | :--- | :--- |
| **Endpoint** | `POST https://api.digishare.ma/v1/campaigns` | `POST https://api-app.digishare.ma/v1/event/campaign` |
| **Response** | The created campaign | `202 Accepted` with an `event_id` |
| **Business errors** (template, sender, balance) | Returned in the response | Not returned: the event is rejected in the background |
| **Payload size** | Large payloads, including base64 files | About 1 MB per event |

::tip
Build and test your payload against the standard API first, because it returns every error immediately. Switch to the asynchronous endpoint once the payload is stable.
::

## Endpoint

**Endpoint**: `POST https://api-app.digishare.ma/v1/event/campaign`

The body is the same JSON object as in the standard Campaigns API. See [WhatsApp Campaigns](/developer-guides/campaigns/whatsapp) and [SMS Campaigns](/developer-guides/campaigns/sms) for every field.

The gateway checks the following rules before it accepts the event:

| Field | Rule |
| :--- | :--- |
| `title` | **Required**. At least 3 characters. |
| `channel` | **Required**. A string such as `whatsapp` or `sms`. |
| `message_template_id` | **Required**, unless the payload carries an inline `message_template`. |
| `recipients` | Must be an array when present. |

::important
The campaign always belongs to the company of the token owner. The API ignores any `company_id` sent in the payload.
::

## Example

The following request queues a personalized WhatsApp campaign and sets an `external_ref` to track it later:

::api-playground
---
method: POST
url: https://api-app.digishare.ma/v1/event/campaign
description: Queue a WhatsApp campaign for background creation.
variables:
  token: YOUR_TOKEN
  senderId: YOUR_SENDER_ID
  templateId: YOUR_TEMPLATE_ID
headers:
  Authorization: Bearer {token}
  Content-Type: application/json
body:
  title: Order Notification Campaign
  channel: whatsapp
  sender_label_id: "{senderId}"
  message_template_id: "{templateId}"
  external_ref: ORDER-BATCH-2026-09-24
  notify_webhooks: true
  global_data:
    name: "%recipient.name%"
    order_id: "%recipient.order_id%"
  recipients:
    - wa_id: "212600000000"
      name: John
      order_id: ORD-123
    - wa_id: "212600000001"
      name: Jane
      order_id: ORD-456
responseSample:
  event_id: acme2633736349319958528
  timestamp: "2026-09-24T10:15:02.133414141Z"
  status: accepted
---
::

## Responses

### Accepted

A `202` response means that the event is queued. The campaign does not exist yet at this point.

```json
{
  "event_id": "acme2633736349319958528",
  "timestamp": "2026-09-24T10:15:02.133414141Z",
  "status": "accepted"
}
```

Keep the `event_id`. The support team uses it to trace what happened to your campaign.

### Errors

Every error response carries an `error` code and a `status`. A `400` also lists every problem in `details`.

| Status | `error` | Meaning | What to do |
| :--- | :--- | :--- | :--- |
| `400` | `invalid_json` | The body is not valid JSON. | Fix the JSON body. |
| `400` | `validation_failed` | A rule from the table above failed. | Fix the payload. Retrying the same payload fails again. |
| `401` | `unauthorized` | The `Authorization` header is missing or malformed. | Send `Authorization: Bearer <token>`. |
| `403` | `forbidden` | The token is invalid, revoked, or expired. | Use a valid token. A newly created token can take a few seconds to be accepted. |
| `413` | `payload_too_large` | The event exceeds about 1 MB. | Split the recipients across several events, or send media as URLs instead of base64. |
| `429` | `rate_limit_exceeded` | Too many events in the current window. | Wait `retry_after` seconds. The `X-RateLimit-*` headers show your quota. |
| `503` | `service_unavailable` | The queue is temporarily unavailable. | Retry after `retry_after` seconds. |

## Tracking the Campaign

The asynchronous API does not return the campaign, so you correlate it with your own reference:

1. Set `external_ref` to an identifier from your system.
2. Set `notify_webhooks` to `true`.
3. Match the `campaign_external_ref` field of the [campaign webhooks](/developer-guides/webhooks) to your identifier.

The campaign also appears in your Digishare dashboard, with the `API` source.

When the background processing rejects an event, for example because of an unknown template, a sender label that does not belong to your company, or an insufficient balance, the platform creates no campaign and sends no webhook. Contact support with the `event_id` to get the exact reason.

::warning
Only the `/v1/event/...` endpoints exist on `api-app.digishare.ma`. Keep every other call, such as `/v1/oauth/token` or `/v1/campaigns`, on `api.digishare.ma`: requests to unknown paths on `api-app.digishare.ma` return `404`, and repeated ones get the calling IP address blocked.
::
